# AI-Enumerator Assistant — Implementation Plan

## 1. Development Strategy

The project should be developed as a **working vertical flow**, not by building every feature independently.

The first complete workflow should be:

```text
Deputy Tahsildar
      ↓
Select Village / Ward
      ↓
Create Layout
      ↓
Generate Houselisting Blocks (HLBs)
      ↓
Review / Edit HLBs
      ↓
Approve Layout
      ↓
Assign Supervisor
      ↓
Supervisor
      ↓
Assign One Enumerator per HLB
      ↓
Enumerator
      ↓
Download Assigned HLB
      ↓
Visit Houses / Buildings
      ↓
Record Household Data
      ↓
Completed / Locked
      ↓
GPS + Field Progress
      ↓
Offline Sync
      ↓
Supervisor Progress
```

The basic workflow must work before implementing advanced AI features.

---

# 2. Core Project Hierarchy

The implementation must follow this hierarchy throughout the backend, mobile application, APIs, database, and UI.

```text
Administrative Area
        ↓
Village / Ward
        ↓
Layout
        ↓
Houselisting Blocks (HLBs)
        ↓
Approximately 250 Houses / Buildings per HLB
        ↓
Supervisor
        ↓
One Enumerator per HLB
        ↓
Household Fieldwork
```

### Important rule

```text
Number of HLBs
      =
Required Number of Enumerators
```

Each HLB should have one primary Enumerator.

The Enumerator should only work with the HLB assigned to them.

# 4. Development Principles

The AI coding agent must follow these principles throughout development.

### Principle 1 — Build working features

Do not create UI screens without implementing the required backend and database functionality.

A feature is complete only when:

```text
UI
+
API
+
Database
+
Validation
+
Error Handling
+
Offline Support where required
+
Testing
```

are working together.

---

### Principle 2 — Build one phase at a time

Do not start advanced AI features before the core workflow works.

---

### Principle 3 — Preserve working functionality

When adding a new feature:

* Do not unnecessarily rewrite working modules.
* Do not remove existing functionality.
* Do not change API contracts without checking dependencies.
* Do not replace working code simply for stylistic reasons.

---

### Principle 4 — Human-written code quality

The code generated by the AI coding agent must look and behave like **well-written human software**, not automatically generated demo code.

The agent must:

* Use meaningful variable and function names.
* Keep functions reasonably small.
* Separate responsibilities.
* Avoid unnecessary abstraction.
* Avoid duplicate code.
* Use reusable components where genuinely useful.
* Write clear business logic.
* Add comments only where they explain non-obvious logic.
* Follow consistent project conventions.
* Handle errors explicitly.
* Avoid placeholder implementations in production paths.
* Avoid unnecessary generated boilerplate.
* Avoid extremely long files where code can be logically separated.
* Keep database queries understandable.
* Keep API handlers thin when business logic belongs in services.
* Use clear models and schemas.
* Write tests for important business rules.

The code should be understandable to another developer who did not generate it.

Do not add comments such as:

```text
// AI generated code
// This function was created by ChatGPT
// Magic happens here
```

Comments should explain the **reason for the logic**, not the fact that AI generated it.

---

```text

```

---

## Processing

```text

    ↓
Load Houses
    ↓
Load Roads
    ↓
Clip Houses to Area
    ↓
Apply Target Count
    ↓
Group Nearby Houses
    ↓
Consider Roads / Geographic Separation
    ↓
Create Candidate HLBs
    ↓
Validate
    ↓
Rank Candidates
    ↓
Return Suggestions
```

---

## Validation

Every generated HLB should be checked for:

* House count
* Boundary containment
* Geographic continuity
* Unassigned houses
* Duplicate assignments
* Very small blocks
* Very large blocks
* Geographic fragmentation
* Road/network practicality

## Output

```text

Boundary
House count
House membership
Validation status
Warnings
Generation metadata
```

## Important Rule

AI-generated HLBs are **suggestions**.

The final workflow is:

```text
AI Generates

Deputy Reviews
      ↓
Deputy Edits if Required
      ↓
Deputy Validates
      ↓
Deputy Approves
```

# 31. AI Coding Agent Rules

The AI coding agent must follow these rules throughout the project.

### Rule 1

Read all project knowledge-base documents before implementation.

The knowledge base includes:

```text
Project Requirement Document
Technical Requirement Document
App Flow
UI/UX Design Document
Backend Schema
Implementation Plan
```

---

### Rule 2

Treat the following hierarchy as authoritative:

```text
Village/Ward
    ↓
Layout
    ↓
HLBs
    ↓
Houses/Buildings
    ↓
Enumerator Fieldwork
```

---

### Rule 3

Do not change the three-role structure without explicit approval.

```text
DEPUTY_TAHSILDAR
SUPERVISOR
ENUMERATOR
```

---

### Rule 4

The Deputy Tahsildar is the final approver of generated layouts.

AI must not automatically approve a layout.

---

### Rule 5

The target house count must remain configurable.

Default:

```text
≈250 houses/buildings per HLB
```

Do not hard-code `250` throughout the codebase.

---

### Rule 6

The number of required Enumerators must be derived from the number of HLBs.

```text
Required Enumerators = Number of HLBs
```

---

### Rule 7

An Enumerator must only access their assigned HLB.

This must be enforced by the backend.

---

### Rule 8

Core Enumerator fieldwork must work offline.

---

### Rule 9

Offline changes must be stored safely and synchronized later.

---

### Rule 10

Synchronization must be idempotent.

Repeated requests must not create duplicate records.

---

### Rule 11

GPS must never be treated as absolute proof that a household was interviewed.

GPS should be treated as a coverage/field-movement indicator.

---

### Rule 12

Voice AI must never silently save uncertain extracted information.

The Enumerator must be able to:


### Rule 17


### Rule 18 — Human-Written Code

All generated code must follow professional human development practices.

The AI should write code that a student developer or professional software engineer could reasonably maintain.

Use:

* Meaningful names
* Clear functions
* Clear classes
* Small focused modules
* Proper separation of concerns
* Reusable components
* Proper error handling
* Consistent formatting
* Meaningful tests
* Simple business logic
* Clear API contracts

Avoid:

* Giant files
* Giant functions
* Copy-pasted code
* Unnecessary abstractions
* Over-engineering
* Random helper classes
* Unused dependencies
* Unused variables
* Repeated API logic
* Hard-coded business values
* Hard-coded credentials
* Fake/mock logic in production paths
* Excessive comments
* Comments explaining obvious code

The code should be **clean, readable, maintainable, and understandable without knowing that AI generated it**.

```text
Why alternative was not selected
```

* Why route optimization is restricted to the assigned HLB
* Why approved layouts are versioned

# 33. Final Development Principle

The project should be built as:

> **A simple, reliable census field application first; an AI-powered system second.**

The core field workflow must be stable before advanced AI is introduced.

The final system should combine:

```text
Official Census-style field UX
          +
GIS-based HLB planning
          +
AI-assisted block generation
          +
One-Enumerator-per-HLB workflow
          +
Offline-first fieldwork
          +
GPS boundary monitoring
          +
Route optimization
          +
Tamil/English voice assistance
          +
Supervisor monitoring
```

The implementation should remain simple enough for another developer to understand, test, maintain, and extend without needing to understand how the code was generated.
